Mastering AWS EC2

Managing Elastic IPs, Resizing Instances & EBS Block Storage

Sushil Yadav 4 min read · Published on AWS Learning Journey

A Hands-On Guide to Static IPs, Vertical Scaling, and Amazon EBS Architecture

Once your EC2 instances are up and running, operational efficiency depends on three core pillars: network consistency, performance scalability, and durable data persistence.

This guide covers how to allocate permanent static IP addresses, vertically scale compute resources on demand, and design, attach, and mount EBS block storage volumes across both Linux and Windows environments.

1. Managing Elastic IPs (Static Public IPv4)

By default, an EC2 instance’s public IPv4 address is ephemeral — AWS releases it back to the pool whenever the instance stops, assigning a new one upon startup. For web servers, DNS configurations, or API endpoints requiring a static entry point, use an Elastic IP (EIP).

Step-by-Step Configuration:

  1. Allocate an Elastic IP:
    • Open the EC2 Dashboard and navigate to Network & Security > Elastic IPs in the left sidebar.
    • Click Allocate Elastic IP address. Leave default network border group settings intact and click Allocate.
  2. Associate with Your Instance:
    • Select your new Elastic IP, click the Actions dropdown, and choose Associate Elastic IP address.
    • Under Resource type, select Instance. Pick your running target instance, select its private IP, and click Associate.
  3. Disassociate and Release (Cost Optimization):
    • Navigate to Actions > Disassociate Elastic IP address.
    • Immediately select Actions > Release Elastic IP addresses to delete it from your pool.
Important Billing Note: AWS charges for allocated Elastic IPs that are not actively associated with running instances. Always release unused Elastic IPs to avoid idle hourly fees.

2. Resizing an EC2 Instance (Vertical Scaling)

Workload requirements fluctuate. If your application needs more vCPUs, higher memory bandwidth, or better network throughput, you can change the instance type (e.g., scaling from a t3.micro to a t3.small or compute-optimized family).

Step-by-Step Procedure:

  1. Stop the Instance: Modifying instance hardware attributes requires a stopped state. Navigate to Instances, select your machine, click Instance state, and choose Stop instance. Wait until the status displays Stopped.
  2. Modify the Instance Type: With the stopped instance selected, click the Actions dropdown and navigate to Instance settings > Change instance type.
  3. Apply the New Configuration: Choose your target instance type from the dropdown and click Apply.
  4. Restart: Select the instance, click Instance state > Start instance, and verify operational connectivity.

3. Storage Architecture: Understanding Amazon EBS

Amazon Elastic Block Store (EBS) provides persistent, high-performance block-level storage designed specifically for EC2. Unlike instance store volumes (which are ephemeral and wiped on stop), EBS volumes persist independently of instance life cycles.

Key Architectural Concepts:

  • Block Storage Paradigm: EBS functions like raw, unformatted physical storage drives connected over a high-speed, dedicated network fabric.
  • Root vs. Additional Volumes:
    • Root Volume: Hosts the guest OS, bootloader, and core system files (typically deleted upon instance termination unless configured otherwise).
    • Secondary Volumes: Created and attached for user databases, application files, and logs that must persist across instance lifecycle rebuilds.
  • The Availability Zone (AZ) Rule: An EBS volume can only be attached to an EC2 instance located within the exact same Availability Zone. Native cross-AZ attachment is not supported.
  • EBS Snapshots: Point-in-time backups stored reliably in Amazon S3. Snapshots are incremental, meaning only blocks that changed since the last snapshot are stored, optimizing backup windows and storage costs.

4. Provisioning, Backing Up, and Mounting EBS Volumes

Step 1: Provision and Attach the Volume

  1. In the EC2 console under Elastic Block Store, navigate to Volumes > Create volume.
  2. Select the volume type (e.g., General Purpose SSD gp3), define the size in GiB, and ensure the Availability Zone matches your running EC2 instance. Click Create volume.
  3. Once the status transitions to Available, select the volume, click Actions > Attach volume, select your target instance, and note the device mount path (e.g., /dev/xvdf or /dev/sdf).

Step 2: Create a Point-in-Time Backup

To capture a clean baseline backup before writing data, select the volume, click Actions > Create snapshot, enter a descriptive label, and select Create snapshot.

Step 3: Format and Mount Within the Operating System

Attaching a block volume is the hardware equivalent of plugging in an unformatted drive; you must initialize the partition and mount the filesystem before use.

For Linux Environments (SSH):

# 1. Inspect block devices to locate the new disk (e.g., xvdf or nvme1n1)
lsblk

# 2. Check if the disk already has an existing filesystem
sudo file -s /dev/xvdf

# 3. Create an XFS file system on the device
sudo mkfs -t xfs /dev/xvdf

# 4. Create the target mount directory
sudo mkdir -p /mnt/data

# 5. Mount the device to the directory
sudo mount /dev/xvdf /mnt/data

# 6. Verify mount status and storage capacity
df -h
Production Tip: Add the device UUID (found via sudo blkid) to /etc/fstab to automatically persist mounts across system reboots.

For Windows Environments (RDP):

  1. Connect via RDP and open Disk Management (Press Win + R, type diskmgmt.msc, and hit Enter).
  2. Find the newly attached drive displaying an Offline status. Right-click and select Online.
  3. Right-click the drive, select Initialize Disk, and choose the GPT partition style.
  4. Right-click the unallocated capacity, select New Simple Volume, assign a drive letter (e.g., D:), and complete the NTFS format wizard.

Wrapping Up

  • Elastic IPs decouple public networking from instance lifecycle states.
  • Vertical Scaling enables dynamic right-sizing without data loss or reconfiguration.
  • Amazon EBS & Snapshots separate compute from stateful storage, forming the foundation for resilient disaster recovery strategies.
Clean-Up Checklist: When finishing lab exercises, unmount and delete test EBS volumes and release unassociated Elastic IPs to eliminate recurring background charges.
